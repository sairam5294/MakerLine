# Contributing to MakerLine

Thanks for helping make AI tools think like senior product designers. Contributions of every size are welcome: a fixed typo in a skill, a new rule backed by a real failure, a case study, or a whole adapter.

## Ground rules

1. **Edit the source only.** Everything lives in `plugin/`. `template/` is generated by `python3 scripts/sync.py`; CI fails if it is out of date.
2. **Every rule needs a reason.** A new standard or check must cite a real failure you saw (link an issue, an eval run, or a line in `LESSONS.md`). Rules nobody has ever tripped over get removed.
3. **Checks over prose.** If a rule can be enforced by a hook, lint, test or CI step, add that alongside the words.
4. **Keep the always-loaded text small.** Skill and agent descriptions are loaded into every session. Read `plugin/skills/product-standards/references/context-budget.md` before adding to them.
5. **Accessible by default.** Anything that renders (starters, portfolio dashboard, docs) must pass axe and meet WCAG 2.2 AA. The kit practises what it preaches.
6. **No personal data.** Never commit `owner/OWNER.md`, API keys, or real project data. Use the example and sample files.

## How to contribute

### Report a problem or suggest a rule
Open an issue using the matching template. For a rule, include the failure it prevents and, if you can, the check that would catch it.

### Change a skill, agent or standard
1. Fork and branch from `main`, named `<type>/<Mon>-<DD>-<summary>` (e.g. `skill/Oct-19-engineering-docs`; `scripts/branch.sh skill "engineering docs"` makes one). Types: feat · fix · content · design · security · a11y · docs · test · ci · deps · refactor · perf · chore · skill · release · eval. CI rejects other names.
2. Edit files under `plugin/`.
3. Run the kit checks locally:
   ```bash
   python3 scripts/sync.py
   bash tests/hooks.test.sh
   ```
4. If you changed `evaluate-idea`, `quality-review`, `new-idea`, the scoring rubric or a reviewer agent, re-run the relevant evals (`evals/RUNBOOK.md`) and paste the result in your PR.
5. Open a pull request using the template. One change per PR keeps review fast.

### Add an adapter for another tool
Adapters live in `scripts/sync.py` (what to copy where) and `template/` (the files each tool reads). Add a short section to `GETTING-STARTED.md` and a test that the generated files parse.

### Add a case study
Add a folder under `examples/<project>/` with the discovery brief, evaluation, what shipped, and what the kit got wrong. Strip anything private.

## Releasing (maintainers)
`./scripts/release-kit.sh <version> "what changed"` syncs, tests, bumps the version, writes the changelog line, rebuilds the plugin and commits. Versions follow semver: PATCH for wording and fixes, MINOR for new skills, agents or checks, MAJOR for changes that break existing projects.

## Code of conduct
This project follows the [Contributor Covenant](CODE_OF_CONDUCT.md). Be kind; assume good intent.
