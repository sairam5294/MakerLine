# Design Direction

Owner is a senior UX designer: act as a design partner who does the groundwork and proposes options; they lead taste and make the calls. This is a **draft direction**, not the design system (that comes after approval, in design-system).

Allowed before approval: everything lands in `docs/` and `design/`, which the approval gate permits. The wireframes double as the prototype for validate-idea.

1. **Read** PROJECT_BRIEF (feel, references, platforms), EVALUATION (personas, positioning, wedge, MVP cut), COMPETITORS (leaders, complaints), CLARITY. Ask ≤ 3 questions only if something blocks direction (e.g. "phone-first or desktop-first?"); otherwise state the assumption and log it in CLARITY.md.
2. **Experience principles** — 3–5, derived from positioning and personas. Each: one line, "this means…", "this doesn't mean…". They're the tie-breakers for every later design decision.
3. **Competitor UX teardown** — for the 2–3 leaders in COMPETITORS.md: first-run steps, steps to the core action, patterns worth borrowing, and the pain points from their review complaints this design must avoid. Cite.
4. **Information architecture** — navigation model (tabs, sidebar, single flow) with the reason, and a sitemap (Mermaid).
5. **Core flows** — 2–4 journeys as Mermaid flowcharts: first run → first value (the "aha"), the core action, and one recovery path (error, offline, permission denied). Count the steps to the core action; compare with the leaders.
6. **Screen inventory** — every MVP screen: purpose · primary action · key content · states (empty, loading, error, offline, success) · MVP or later.
7. **Content and voice** — tone in 3 words with do/don't, a terminology list (one word per concept), and real microcopy for the key moments: onboarding promise, empty states, the main error, the success moment.
8. **Visual directions** — 2–3 distinct options, each: name, mood words, palette (with text/background pairs and contrast ratios, ≥ 4.5:1 for text), type pairing, shape and spacing feel, imagery and iconography, motion, one reference product. Recommend one and say why; follow platform conventions (Apple HIG / Material 3) where the brief targets native apps. Never imitate a specific brand's identity.
9. **Accessibility and inclusion plan** — from personas and EVALUATION §11: the persona spectrum (permanent, temporary, situational), languages and scripts, text scaling, low vision and screen readers, motor (targets, one-handed, no drag-only), cognitive (plain language, one task per screen, no time pressure — W3C COGA), low connectivity, older adults or children if relevant. Apply `../product-standards/references/inclusion.md` (global baseline: accessible worldwide, no discrimination — names, gender, languages, low-end devices, cost). State the conformance target (WCAG 2.2 AA everywhere, plus what launch markets add) and lock in the "cheap now, expensive later" choices. Add accessibility notes to each wireframe (heading, focus order, what the screen reader says for icons and status).
10. **Wireframes** — copy (`cp`) `references/wireframe-template.html` to `design/wireframes/index.html`; read only its HOW TO FILL comment and one example screen, then fill it (Standard ≤ 8 screens, Deep 12+; delete the comment when done): one section per MVP screen in grey-box fidelity with real content (no lorem ipsum), at least one empty and one error state, links that click through the core flow, and a designer note per screen (what it's for, open questions). Phone frames for mobile products, desktop width for web tools. Keep the markup accessible (landmarks, labels, real buttons). Run `check_idea_pack.py` (product-kickoff/scripts) for labels, links and states; if a browser is available, also open it, check every screen renders and the core flow clicks through, and fix what's broken.
11. **Figma (optional)** — if the Figma connector is available and the owner wants it, build the wireframes in a new Figma file (load the figma-use and figma-generate-design skills first; grey boxes, auto-layout, one frame per screen, flow arrows); link it in the doc.
12. **Write** `docs/product/DESIGN_DIRECTION.md` from `references/design-direction-template.md`. Present in ≤ 12 lines: principles, the recommended visual direction, steps to the core action vs leaders, the wireframe link, and 2–4 design decisions for the owner.
13. Update CLARITY.md (new questions, especially ones a prototype test could answer) and STATUS (Design direction: Waiting for owner → Done once they pick a direction). Offer validate-idea (prototype test with these wireframes) or the approval gate.

After approval, design-system turns the chosen visual direction into tokens and components; write-prd links screens to stories.
