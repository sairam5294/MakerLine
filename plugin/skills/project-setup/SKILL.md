# Project setup

Gate: STATUS `Evaluation: APPROVED`; TECH_STACK, DESIGN_SYSTEM (or BRAND), PRD (full) and the engineering docs exist. Phase 7b. Templates in `templates/`.

Why: one shared source of truth that every tool reads. AGENTS.md and `docs/` hold the rules once; each tool's folder (`.claude/`, `.cursor/`, `.github/`) only points to them and adds what that tool needs, so Claude, Cursor, Codex, Copilot and ChatGPT follow the same rules without copies drifting apart.

## Steps
1. **Read** TECH_STACK.md, `docs/ARCHITECTURE.md`, `docs/DATABASE.md`, `docs/CODE_STYLE.md`, `docs/RULES.md`, BRAND.md / DESIGN_SYSTEM.md, TOOL_PLAN.md (if any), and the starter's own files if the project came from a kit starter. Use the real stack, folders, commands and services — never generic placeholders.
2. **Folder structure** → `docs/STRUCTURE.md` from `templates/STRUCTURE.md`: the tree to two or three levels with a one-line purpose per folder, a "where does X go?" table (component, screen/route, API call, hook, store, type, constant, string, test, migration, asset, doc), naming rules, and what must never be created (e.g. a second `utils/`, files over ~300 lines without a reason). Create the empty folders the tree promises (with a `.gitkeep` only where a folder must exist before code).
3. **Environment** → `.env.example` from `templates/env.example`: every variable the stack uses, grouped by service, each with inline comments — what it is, where to get it (dashboard path), public or secret (and why a public one is safe), which environments need it, required or optional, example format. Never a real value. `.env*` stays git-ignored except `.env.example`. Note where production values live (Vercel/Supabase/EAS dashboards, GitHub Actions secrets).
4. **Setup guide** → `docs/SETUP.md` from `templates/SETUP.md`: prerequisites with version-check commands; get the code (git clone, GitHub CLI, or Download ZIP — and what ZIP loses: no git history, no hooks until `git init`); install; env; local database; run; test; common errors and fixes; deploy (preview and production for this stack); rollback. Each step has the exact command and what "it worked" looks like.
5. **README** → `README.md` from `templates/README.md`: what it is and who it's for, screenshot slot, features, tech stack, quick start (5 commands max, linking SETUP for detail), scripts table, folder summary (link STRUCTURE), docs index (link `docs/README.md`), accessibility statement link, contributing (branch convention), licence. Plain language, no badges you can't keep green.
6. **GitHub rules** → `docs/GITHUB.md` from `templates/GITHUB.md`, plus `.github/` files from `templates/github/`: PR template (already in the kit template), `CODEOWNERS`, `copilot-instructions.md` (points to AGENTS.md), workflow `repo-health.yml` (monthly, read-only report: repo size, Actions storage, stale branches, open PR age). Fill free-tier limits only from the vendors' current pages, with the date checked.
7. **AI tool folders** (one source, thin pointers):
   - `AGENTS.md` stays the shared rulebook (Codex reads it natively; Claude via CLAUDE.md; Copilot via `.github/copilot-instructions.md`).
   - `.cursor/rules/`: write `project.mdc` (always applied: stack in one line, import aliases, hard rules with their enforcement, and the **rule index** table of every scoped rule and the globs it attaches to) and one scoped `.mdc` per area that exists in this project, from `templates/cursor-rules/`: architecture, components, design, data-api, forms-validation, errors-logging, permissions, i18n, dates-time, accessibility, security, testing, ai-features. Each: frontmatter `description` + `globs` for the real folders, the project's actual patterns with one short example, an "Enforced by" table (lint / hook / CI / review only), and "never" lines. Skip areas the project doesn't have. Don't duplicate the kit's own rules (`product-workflow`, `security-backend`, `testing`, `ui-accessibility-ux`) — link them.
   - `.claude/`: `CLAUDE.md` stays `@AGENTS.md` + Claude notes; add project skills in `.claude/skills/` from `templates/claude-skill/SKILL.template.md` for the 1–3 jobs this project repeats most (e.g. "add a screen", "add a table + RLS + migration", "add a translated string") — each a short step list using this project's real paths and commands.
   - `docs/CONTEXT_PACK.md` from `templates/CONTEXT_PACK.md`: ≤ 1 page for tools that can't read the repo (ChatGPT in the browser, a contractor): the product in 5 lines, stack, rules that matter, terminology, where answers must go back. Regenerate when RULES or BRAND change.
8. **Check:** a fresh clone → follow SETUP.md literally in a clean folder (or the kit's `scripts/new-project.sh` output) and confirm `install → run → test` works; every `.mdc` glob matches at least one existing path (`ls` the globs); every env var in code appears in `.env.example` (grep `process.env.` / `Deno.env` / `import.meta.env`); no secret values anywhere; branch name and hooks work (`scripts/check-branch.sh`).
9. Present in ≤ 10 lines; update `docs/README.md` index, STATUS `7b Project setup: Done`, DECISIONS. Offer plan-build.

Keep current: build-feature updates STRUCTURE and `.env.example` when it adds a folder or variable; quality-review checks code against the scoped rules; standards-refresh re-checks GITHUB.md limits.
